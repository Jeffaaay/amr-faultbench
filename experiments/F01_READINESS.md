# 第一个可运行实验：TPDO 反馈丢失

状态：实施前验收说明；NOT_RUN。实施窗口仍为 2026-10-26 至 11-01。10/25 schema 冻结和具体源码版本选择是前置条件。

要回答的问题：一侧电机反馈消失后，控制器有没有发现、有没有进入限制运动的状态，以及反馈恢复后是否仍遵守恢复条件。

## 固定范围

- 两个虚拟轮驱动节点，DS402 的必要状态、SDO 请求/响应、NMT、心跳、目标速度、TPDO 反馈。
- 第一个故障完整名称 `F01_TPDO_DROPOUT`。丢弃一侧 TPDO，同时保留心跳，避免把心跳丢失误当作 TPDO 检测。
- 控制器要么是获准提取的主机可测试逻辑，要么是独立行为模型。独立模型必须标记 model-only；完成源码行为对照前不能称为 STM32 固件验证。
- 不连接真实 CAN 适配器、不开放物理串口、不访问真实机器人。vcan 是传输工具，不能直接执行 STM32 固件。

## 输入与证据

每次运行保存完整 manifest：源码与配置摘要、harness/模型/策略/evaluator 的提交，schema 版本，随机种子，故障起止与目标节点，虚拟时钟定义，终止条件，以及结果输出路径。未知必填版本不得自动填成 latest。

所有时序值从所选基准导入并审查。补充说明中的“TPDO every 25 ms”是示例，不能覆盖审计得到的实际配置；控制周期也不能直接当成反馈周期。

故障时间计划与实际注入要分别记录。虚拟节点的发送记录和接收路径上的丢弃计数用于证明注入确实发生；控制器检测记录必须由控制逻辑产生，不能由注入器代写。

## 验收与失败定义

| 项目 | 判定依据 | 不允许的捷径 |
| --- | --- | --- |
| 已注入 | 目标节点、指定窗口、实际丢弃事件、其他流仍正常 | 只有配置文件写了 dropout |
| 已检测 | 独立控制器状态/故障事件，关联到反馈过期 | 注入器自己输出 detected=true |
| 安全响应 | 撤销非零目标、进入限制态；保留停止请求及确认的不同状态 | 写了 STOP 就宣称物理停稳 |
| 允许恢复 | 双侧新鲜反馈、状态确认、既有互锁、明确授权 | 反馈一回来自动重新运动 |
| 无意外转换 | 独立 evaluator 检查完整转换记录 | 只查最后一个状态 |
| 完整证据 | Trace、manifest、evaluator 输出及丢失计数 | 丢日志的运行按完整成功计算 |

至少包括正常无故障、单侧/双侧丢失、阈值前后边界、短时恢复又丢失、反馈乱序/旧帧、无法确认停稳、恢复未授权等检查。检测时间预算需包含调度量化与已知迟延；不能直接承诺“恰好在配置阈值时刻检测”。

未来预定入口：`python run_experiment.py --fault F01`。该命令尚未实现，不能当作现在可运行的操作说明。

机器输出至少区分 PASS / FAIL / INCONCLUSIVE / INVALID，并包含 evidence_level（synthetic / model / extracted_logic / HIL / robot）、fault_injected、fault_detected、stop_requested、stop_confirmed、unexpected_transitions、capture_complete。无证据时使用 unknown/null，不能默认通过。

首个模型通过只证明测试闭环能跑，不能证明制动性能、真实固件安全或 Agent 优势。

补充：tools/trace_review.py 已能离线检查草案记录。它不是此文件预定的 run_experiment.py，也未实现 F01 控制器/注入器。SAFE_STOP、停止观测和复位完成须分开；wheel_feedback 停止证据不能冒充车体物理测量。
